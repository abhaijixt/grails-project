The problem

Knowledge transfer fades.
Docs drift silently.

Nothing breaks when documentation goes stale. No test fails, no pipeline turns red. It just quietly stops being true — and the people who would notice are the ones who already left.

01

KT lives in a person

A handover session, a recording nobody rewatches, and a Confluence page written the week someone was leaving.

02

Docs are a snapshot

Accurate the day they were written. The code kept moving; the document did not. Nothing enforced the gap closed.

03

Drift is invisible

There is no failing signal. The first person to discover it is a new joiner trusting a page that lies to them.

What that looks like concretely — this repo, one hour ago. A developer added a field to Book.groovy. The design doc still described the old shape:

- Book.groovy declares String publisher
- docs/LLD.md, published mentions it 0 times

Nothing failed. The site kept building. The page just became quietly wrong.

What it is

Three parts. Two are
boring on purpose.

PART 01

Docs as code

Markdown lives in docs/ beside the source. MkDocs + Material builds it into a static site. Same repo, same PR, same review.

10 Markdown files · 1 config · 0 servers

PART 02

Drift check at PR time

On a pull request, Claude reads the code diff and the current docs, and reports which sections the change made stale — and why.

Reads the diff · proposes edits · never merges

PART 03

Human approval, always

The proposal arrives as a normal reviewable change. A person reads it and approves it. That step is never automated away.

Advisory only · a human merges

Parts 1 and 3 are deliberately unremarkable — they are just Git and code review. The only new thing is part 2, and it produces suggestions, not commits.

Why bother

Four arguments,
one of them selfish.

01

Onboarding gets faster

A new joiner reads a design doc that is provably current, instead of asking someone who has to remember. The HLD, LLD and a file-by-file walkthrough are one URL.

02

Docs get reviewed like code

Doc changes arrive as diffs in the same PR flow. They get the same scrutiny, the same history, the same blame — and the same ability to be rejected.

03

One source of truth

The doc and the code share a commit. There is no second system to keep in sync, and no question about which copy is current.

04

Near-zero new infrastructure

No wiki to license, no server to run, no database. A workflow file, a pinned requirements file, and a branch. That is the entire footprint.

41lines in the entire deploy workflow
6pinned pip packages, no other deps
23sreal build + publish time on CI
$0hosting — GitHub Pages, static

How it works

The loop.

Six steps. The green one is a human and stays that way. NOW is what I ran locally with Claude Code to build this demo; ORG is where it moves once it runs in Codefresh against GHE.

STEP 01 Pull request opened NOW local branch
ORG GHE pull request
STEP 02 Drift check runs NOW Claude Code, my machine
ORG Codefresh pipeline step
STEP 03 Claude proposes doc fix NOW edits in working tree
ORG bot commit / PR comment
STEP 04 Human reviews & approves Never automated.
A person reads the diff.
STEP 05 Merge to main NOW git merge --no-ff
ORG protected-branch merge
STEP 06 Publish automatically NOW GitHub Actions
ORG Codefresh → internal host

The loop closes on itself: step 06 republishes the docs that step 03 proposed and step 04 approved. Nothing in the chain can write to main without a human in step 04.

Rollout

Four phases.
Automation comes last.

Deliberately ordered so the value lands before any pipeline work, and so we learn what a good drift check looks like before we let one run unattended.

PHASE 01

Seed the docs

Turn existing KT notes, handover decks and recordings into Markdown in the repo. Rough is fine — the point is to get it into Git where it can be reviewed and improved.

PHASE 02

Publish it

Add MkDocs and a deploy job. The team gets a real docs site on day one. This phase alone is already worth doing, with no AI involved at all.

PHASE 03

Calibrate by hand

Run the drift check manually on real PRs. Compare what it flags against what a reviewer would flag. Tune until the false-positive rate is boring.

PHASE 04

Automate — flag-only

Move it into Codefresh as a pipeline step that comments on the PR. Flag-only first. Suggestions come later, and only once phase 03 has earned it.

Phases 1–2 are what this demo already proves end to end. Phase 3 is the honest cost: it is judgement work, and it is where the effort actually goes.

Guardrails

What it is allowed to do.

LEVEL 1

Flag only — where we start

The check comments on the PR: “these doc sections look stale, here is why.” It writes no files. A human decides whether it is right and does the edit.

LEVEL 2

Suggest — where we go next

It proposes the actual doc diff, as a suggested change or a bot commit on the PR branch. Still requires a human approval before anything merges. This is what the demo you just saw does.

LEVEL 3

Autonomous — explicitly ruled out

Writing to main without review. We are not proposing this, not in phase 4, not later. Documentation that edits itself unsupervised is a worse problem than documentation that is stale.

+ the pipeline is advisory — it comments and proposes
- the pipeline never blocks a merge, never gates a release

If the drift check is wrong, noisy, or down, the worst outcome is an ignorable comment. It has no power to stop anyone shipping.

The ask

One repo. Two secrets.
Two pipeline specs.

ASK 01

One pilot repo

A single service with real KT debt and an active team. Not a greenfield toy — the value only shows where drift actually happens.

ASK 02

Two secrets

An Anthropic API key, and a bot token with PR comment access. Both scoped to the pilot repo, both revocable.

ASK 03

Two pipeline specs

One to publish the docs site on merge. One to run the drift check on PRs, flag-only. Both are small enough to read in a sitting.
